# Contributing

## Development Setup

1. Install Go `1.26.4+` (the toolchain version in `go.mod`).
2. Clone the repository. There are no third-party dependencies to install.
3. Keep build caches inside the checkout:

```bash
export GOCACHE="$(pwd)/.gocache"
export GOMODCACHE="$(pwd)/.gomodcache"
```

## Branch Promotion Flow

- Branch feature, bugfix, and chore work from `dev`.
- Merge reviewed work into `dev` after the `unit` check passes.
- GitHub Actions opens a promotion PR from `dev` to `staging` after green pushes on `dev`.
- Merge `dev -> staging` only after `unit` and `integration` both pass.
- GitHub Actions opens a promotion PR from `staging` to `main` after green pushes on `staging`.
- Merge `staging -> main` only after `unit`, `integration`, `docs-build`, and `release-prep` pass.
- `dev` allows the repository owner to bypass the PR gate when necessary. `staging` and `main` do not.

Both legs promote through a dedicated branch (`promote/dev-to-staging` and
`promote/staging-to-main`) built from the base tip, so a promotion PR is never
`BEHIND` its base. See [docs/project-docs.md](docs/project-docs.md#promotion-automation) for why.

## Quality Gates

Run the local gate before opening a pull request:

```bash
scripts/verify.sh
```

It owns the command list — generated-output check, `go vet`, tests with native
coverage, the coverage floor, and the docs site build — so no document restates
those commands and they cannot drift apart. `scripts/verify.sh --quick` skips
the docs site build when you have not touched documentation.

- `go generate ./...` must leave the tree clean. `generated_wrappers.go` and
  `docs/sdk-reference/` are both checked in, and both are regenerated by it.
  `scripts/check_generated.sh` enforces this, and every producer of the `unit`
  check runs it, so a generator run that was never committed blocks the PR.
- Coverage is ratcheted per branch. `95.0%` is a permanent floor; if the
  published badge for the base branch is higher, keep coverage at or above that
  higher value.
- `staging` and `main` also require live integration credentials, just like
  protected-branch CI.

## Release Labels and Mainline Releases

- Every `staging -> main` promotion PR must carry exactly one of:
  - `semver:patch`
  - `semver:minor`
  - `semver:major`
- The `prepare-release-promotion` workflow rewrites the promotion branch with the release version bump before merge.
- The required `release-prep` check is non-mutating and verifies that the final promotion PR head is already prepared.
- After the PR merges into `main`, GitHub Actions tags the release as `vX.Y.Z`,
  creates a GitHub Release, and attaches a versioned source zip. The Git tag is
  what `go get` resolves; there is no separate package registry to publish to.

## Contract Sync Workflow

The bundled contract artifacts are shared with
`herooftimeandspace/incident-py-q`. Refresh them from a local checkout and
regenerate everything they feed:

```bash
scripts/sync_from_source_sdk.sh ../incident-py-q
go generate ./...
go test ./...
```

The sync script copies machine-readable artifacts only. Documentation in this
repository is written for Go and is never overwritten by a sync, so Go-specific
notes belong in the Markdown here rather than upstream.

If a sync changes the generated SDK surface, commit the refreshed
`testdata/contract/*_sdk_inventory.json` snapshots, `generated_wrappers.go`, and
`docs/sdk-reference/` in the same change.

## Public API Stability

The public SDK surface (`Client`, `Config`, `RequestOptions`, generated
namespaces and method names, and method signatures) is semver-governed:

- Backward-compatible additive changes: minor version bump.
- Breaking method/namespace/signature changes: major version bump.
- Bug fixes that preserve the public surface: patch version bump.
